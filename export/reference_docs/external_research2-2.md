## 2. Семантическая плотность и «хирургический сплиттинг»

Идея декомпозировать «гигантские» параграфы на атомарные утверждения полностью подтверждается исследованиями по юридическому семантическому поиску в немецком праве: эмбеддинги лучше работают на небольших сегментах, чем на крупных фрагментах текста. [mediatum.ub.tum](https://mediatum.ub.tum.de/doc/1521744/1521744.pdf)

Что можно улучшить:

- Ввести **жёсткий таргет по длине атомарного утверждения** (например, 1–2 предложения, не более N токенов) и проверять его автоматически.  
- Добавить метаданные: для каждого `AtomicRule` хранить ссылку не только на `Paragraph`, но и на мелкую структуру закона: `Gesetz → Teil → Abschnitt → Paragraph → Absatz → Satz → Nummer`. Это даст возможность в ответе показывать «лес, дерево и ветку» одновременно.  

Альтернативная/дополнительная техника:

- В духе «hypothetical question nodes» — генерировать для каждого большого параграфа набор вопросов, на которые он отвечает, и индексировать эмбеддинги именно этих вопросов как отдельных узлов. [linkedin](https://www.linkedin.com/pulse/transforming-access-legal-information-innovative-rag-neo4j-hernandez-vt5ye)
- Это хорошо работает как дополнительный слой к вашим `AtomicRule`: иногда проще найти норму по «типичному вопросу», чем по переформулировке исходного текста.

## 3. Немецкий язык, композиты и морфология

NER + лемматизация — правильная база, но для немецкого юр. языка почти обязательно нужен **decompounding** (разбор составных слов).  

Практические дополнения:

- Подключить морфологический анализ + decompounding (специализированные инструменты или комбинация spaCy/Stanza + кастомные правила).  
- Для каждого сложного термина хранить:
  - исходную форму (`Arbeitsunfähigkeitsbescheinigung`),
  - списки компонентов (`Arbeits` + `Unfähigkeit` + `Bescheinigung`),
  - связку с концепт‑узлом высокого уровня (например, `Arbeitsunfähigkeit` как медицинско‑трудовое понятие).  

Это полезно, потому что:
- работы по немецкой юридической IR показывают, что сочетание классического расширения запроса по юридическому тезаурусу и эмбеддингов сильно улучшает качество поиска. [mediatum.ub.tum](https://mediatum.ub.tum.de/doc/1521744/1521744.pdf)
- вы сможете связывать документы через совпадения подкомпонентов композитов и тезаурусных синонимов, даже если эмбеддинги «промахнулись».

Я бы явно завёл:

- класс `Concept` с типами: `Term`, `Institution`, `Procedure`, `Rechtsgebiet` (отрасль права и т.д.),  
- ребра из текстовых узлов (`AtomicRule`, `Paragraph`) к соответствующим `Concept`.  
Это позволит делать запросы вида: «покажи все нормы, связанные с `Kündigungsschutz` + фильтр по трудовому праву».

## 4. Граф, GDS и латентные связи

Использовать Neo4j GDS для анализа правового графа — отличная идея, она уже практикуется при анализе крупных немецких правовых сетей (case‑law + statutes) в виде citation network в Neo4j. [ca-roll.github](https://ca-roll.github.io/downloads/Analysis_of_a_German_Legal_Citation_Network.pdf)

Что важно учесть:

- Каждый тип ссылки лучше моделировать отдельным типом ребра: `CITES`, `AMENDS`, `IMPLEMENTING_ACT_OF`, `EXCEPTION_TO`, `APPLIES_TO`, `OVERRULES` и т.д. Тогда:
  - PageRank / centrality можно запускать отдельно по нормативным ссылкам, не смешивая их с техническими или редакционными.  
- Версионность: закон меняется, и работы по диахронным эмбеддингам для немецких судов показывают, что язык судов быстро перестраивается после поправок. [aclanthology](https://aclanthology.org/2022.nllp-1.19.pdf)
  - Имеет смысл вести `valid_from`, `valid_to` на нормах и учитывать дату события/кейса в запросе.  

Для GDS‑анализа:

- Я бы почти всё тяжёлое (community detection, global PageRank по всему корпусу) вынес в **офлайн‑precompute**, а онлайн оставил только:
  - локальные similarity‑алгоритмы по соседям уже отобранных кандидатов,  
  - быстрые traversals по заранее посчитанным `[:SEMANTICALLY_RELATED]`.

## 5. Гибридное ранжирование и веса

Ваша формула вида \(Score = w_1 \cdot \text{Vector\_Sim} + w_2 \cdot \text{Keyword\_Match} + w_3 \cdot \text{GDS\_Rank}\) очень разумна как первый шаг.  

Я бы предложил:

- **Нормализация каждого компонента** до общего диапазона (например, \([0,1]\)) перед суммированием:  
  - VectorSim — косинусное сходство → линейная нормализация по top‑k,  
  - KeywordMatch — нормированное BM25/TF‑IDF,  
  - GDSRank — лог‑масштаб PageRank/centrality, чтобы «монстры» не доминировали.  
- Сделать веса \(w_i\) не константами, а функциями типа запроса:
  - запрос‑«definition lookup» — больше веса на `KeywordMatch` и точной цитате;  
  - запрос‑«case reasoning» — больше веса на `VectorSim` и `GDSRank`.  

Если получится достать хоть немного разметки релевантности (например, с датасета GerDaLIR или собственного логирования кликов/подтверждений юристов), можно применить простое **learning‑to‑rank** (LambdaMART, RankNet) поверх ваших признаков. [github](https://github.com/lavis-nlp/GerDaLIR)
Даже небольшой обученный ранкер обычно лучше ручной настройки весов.

## 6. Пайплайн запросов и оркестрация

Технически ТЗ у вас описывает в основном «данные и ранжирование». Я бы явно дописал **путь запроса**:

1. Предобработка запроса:
   - language detection (немецкий/смесь),  
   - NER + вычленение ссылок на конкретные параграфы (§‑ссылки), дат, сущностей.  
2. Построение **концептного профиля запроса**:
   - маппинг обнаруженных терминов/композитов на `Concept`‑узлы.  
3. Гибридный поиск:
   - а) векторный top‑k по `AtomicRule` + вопрос‑узлам;  
   - б) BM25/keyword top‑k;  
   - в) графовое расширение: «подтянуть» соседей по `CITES`, `SEMANTICALLY_RELATED`, общим `Concept`.  
4. Рерэнкинг по вашей формуле +, возможно, дополнительному ML‑ранкеру.  
5. Построение **объяснимого контекста для LLM**:
   - структурированный JSON: какие нормы, какие связи, какая иерархия;  
   - LLM видит не «кучу текста», а уже агрегированную логическую картинку.

Отдельно стоит продумать **feedback loop**: сохранить, какие нормы пользователь использовал в финальном ответе/комментариях, чтобы потом дообучать ранкер.

## 7. Оценка качества и бенчмарки

Чтобы конструктивно «крутить ручки», нужен хотя бы минимальный набор метрик. Здесь вам помогут существующие ресурсы по немецкой Legal IR:

- GerDaLIR — большой датасет для legal information retrieval (немецкие кейсы + запросы + релевантность), отлично подходит как тестовый стенд для ваших гибридных стратегий. [github](https://github.com/lavis-nlp/GerDaLIR)
- Работы по улучшению семантического поиска в немецком праве показывают, что комбинированные подходы (тезарус + эмбеддинги) дают прирост качества по top‑k результатам, что можно воспроизвести в вашей архитектуре. [mediatum.ub.tum](https://mediatum.ub.tum.de/doc/1521744/1521744.pdf)

Практически:

- Завести небольшой, но «золотой» набор запросов + ожидаемых норм (размеченный юристом) и считать nDCG/MAP@k.  
- Параллельно логировать пользовательские клики и ручные «подтверждения»/«отклонения» норм для обучения ранкера и контроля drifts.
